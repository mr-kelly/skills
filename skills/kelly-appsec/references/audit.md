# 选择审计路径

从客户的业务策略与实际症状开始：谁访问了谁的数据、哪个动作、何时、什么环境/版本。若怀疑服务器失陷，保留日志与访问记录并转交 Linux 入侵核查；本技能处理应用/API 的授权和业务缺陷。

## 接口与规则

读取指定版本 OpenAPI/路由定义形成有来源的接口清单，记录 method、path、业务流程、operationId 和具体文件引用。OpenAPI 的 servers/回调/链接均不自动执行；模板路径必须转换为明确受控对象路径才能动态验证。

由业务负责人给出身份×对象×动作×字段×状态的预期。覆盖匿名、用户 A、用户 B、不同租户、管理员、共享/委托例外，以及订单/支付/导出等敏感流程。记录策略依据及未确认的假设。不要默认“登录了就可以访问任何 ID”。

有限动态案例的 allow 需要返回数据断言；deny 需要成功的正向基线、明确禁止的数据断言与拒绝状态。正向基线既可验证调用者自己的对象，也可验证对象所有者的正常访问；准确记录其所证明的前提。返回 200 不等于越权；返回受控其他租户数据并违反确认策略才构成具体规则违反。只返回不符合预期的状态、不含所声明禁止数据时仍是不确定。

## 源码 / 离线审阅

本机 Agent 阅读授权目录中的实际源码，不上传仓库。先确认实际分支与提交，追踪全局认证、中间件、路由权限、服务层、ORM 查询约束及序列化字段；不能因局部路由没有 guard 就宣布未鉴权。沿对象所有权、可信租户标识、管理员动作、字段读写权限、重复提交/幂等与敏感状态转换分别审查。检查依赖/配置可以使用已有工具的明确版本报告，但不要执行仓库附带的不可信安装脚本。

每项审阅至少包含：ruleId、具体版本、文件与行位置、最少必要脱敏摘录、完整权限链推理、assessment(candidate/no-indicators/unverified) 和建议。no-indicators 仍是 unverified 动态结论。完整 SAST、运行时未覆盖路径、注入检测、并发竞态和通用业务滥用不会由这个有限 REST runner 自动完成。

离线文档：

```json
{"schemaVersion":1,"sourceRevision":"rev-a","reviews":[{"ruleId":"RECORD_ID","assessment":"candidate","location":"src/orders/service.ts:42","excerpt":"脱敏后的具体片段","reasoning":"对象查询只有 ID 条件，需要追踪上游租户约束。","severity":"medium","recommendation":"核对全局权限链后添加可信租户约束。"}]}
```

```sh
node scripts/review.mjs --project PROJECT_ID --run OFFLINE_RUN_ID --file review.json --apply
```

## 证据与复测

每项 check 绑定项目、任务、端点、规则、身份、版本与 attempt。证据记录来源/时间、SHA-256、本机文件名、脱敏摘录及限制。真实 Token、Cookie、密钥和客户原始业务数据不写入 Busabase。

动态原件位于本机明确指定目录，默认目录 0700、文件 0600。不要公开或提交这些文件；按客户证据政策管理。网页人工复核需理由，自动候选与人类结论分开。修复复测对应原规则的业务键、方法、路径、身份、策略、断言及正向基线；匹配失败需明确修订映射，不能用其他接口的成功结果关闭问题。
